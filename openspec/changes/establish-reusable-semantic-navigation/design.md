## Context

现有字段语义地图已经具备字段、注释、属性表达、Wiki辅助证据和物理映射，但当前导航Projection把不同语义职责混在同一棵树中。项目又要求保持只读元数据边界、候选与事实分离、Unknown/Conflict可见，以及方法可重放。本设计承接 proposal.md 和 `reusable-semantic-navigation` / `table-semantic-map` 规范，不改变原始物理事实。

## Goals / Non-Goals

**Goals:**

- 建立一个可版本化的金融/衍生品业务导航骨架，并允许不同业务域通过配置扩展。
- 将业务导航、业务概念详情、属性表达、字段属性、限定维度、物理实现和治理队列建模为互相引用的投影，而不是一棵万能树。
- 让字段属性轴能跨概念复用，同时保留业务概念和字段证据。
- 把Wiki和知识骨架限制为可定位的候选/上下文输入。
- 用全局语料发现、代表性案例、反例和独立surrogate review验证导航，而不是按截图逐项加词。
- 保证每次试做、审阅、修改和Projection重建都有版本和证据记录。

**Non-Goals:**

- 不建立企业级正式本体、知识图谱数据库或通用元数据平台。
- 不把金融知识骨架直接当作事实，不以业务常识替代字段、注释、表结构和Wiki证据。
- 不把当前TRADEFLOW配置推广为所有Schema的业务真理。
- 不在本Change中查询业务数据行、修改源系统、启用LLM自动写回或改变现有Canonical事实。
- 不以“待归类”数量下降作为唯一成功标准。

## Decisions

### 1. 采用“主导航 + 概念详情 + 正交轴 + 治理队列”四层投影

主导航按金融/衍生品业务区域组织：参与主体、产品与标的、询价/订单/交易、合同与结构、生命周期、持仓与风险、估值与履约保障、执行/清算/结算、参考配置、运营报表与数据加工。一个概念允许多个入口。

概念详情单独展示：

```text
业务概念
├─ 属性表达
├─ 字段属性
├─ 限定维度
├─ 业务上下文/相关概念
└─ 物理实现
```

这样“名义本金—动态名义本金”和“名义本金—金额属性”不会被误画成同一种父子关系。

页面顶部另设六段生命周期主线：交易准备、交易达成、合同存续、估值风控、清算结算、运营治理。它回答“当前处于哪个业务阶段”；十个业务区域回答“正在看哪类业务对象或能力”。二者通过多入口引用连接，均不得成为唯一归属或正式本体关系。

读者页面固定为三栏职责：左栏显示当前阶段的核心对象、业务事件和跨环节关联；中栏显示当前概念、候选定义、属性表达和正交筛选；右栏显示选中表达的限定条件、业务上下文、物理实现及逐项证据。治理队列独立于业务树展示。

### 2. 业务骨架与属性轴分开配置

业务骨架配置只定义导航区域、候选入口、同义词和允许的上下文；字段属性配置定义标识、角色、状态、方向、计量、币种、时间、配置、审计等可复用轴及其开放候选规则。两者都不直接发布事实。

替代方案是把所有词放入一张分类词表；该方案被拒绝，因为它会把业务词、字段后缀、限定词和Wiki目录词混成封闭分类，并且无法解释跨Schema的新形态。

### 3. 先中心词/概念证据，再修饰词/属性证据

字段表达解析先识别可能的业务概念和稳定表达，再识别属性轴与限定；事件词、角色词和Wiki路径只能作为修饰或上下文候选，不能抢占中心概念。无法完成中心概念确认时，输出开放候选和原因，而不是强行落入业务区域。

### 4. 保留候选、发布Projection和审阅决策三类输出

候选输出保留全量观察表达、开放修饰词、匹配信号、反证和Unknown。发布Projection只消费满足发布条件的候选；人工决策单独版本化，不能覆盖原始观察。页面同时提供候选/发布切换和原因筛选。

### 5. 以多组案例驱动规范，而不是以单一名义本金驱动

最小试做至少包含：名义本金（度量和多限定）、交易对手（主体/角色和标识属性）、交易或订单（对象/事件边界）、持仓或保证金（状态/生命周期/风险），并加入字段后缀误导、同名异义、Wiki冲突和纯结构相似反例。第二Schema或第二业务配置用于检查复用性。

### 6. 独立surrogate review必须审阅读者结果

审阅不只检查Schema、数量和测试；还要看主导航是否符合金融业务理解、概念详情是否能解释字段属性、待归类原因是否有用、冲突是否可见、同一概念能否多入口复用，以及是否存在“词命中即分类”的反例。每轮记录ACCEPT、REWORK、STOP或DEFER及最小下一步。

## Risks / Trade-offs

- [Risk] 金融业务骨架可能被误当成已确认业务本体 → [Mitigation] 标记为版本化导航候选/配置，任何落地概念仍需物理和Wiki证据，发布层显示证据状态。
- [Risk] 业务导航区域之间存在重叠，例如生命周期与清算结算 → [Mitigation] 允许多入口，用上下文和入口职责区分，不强迫唯一归属。
- [Risk] 开放属性轴会增加待复核数量 → [Mitigation] 按原因拆分队列并优先处理高覆盖、高风险和可验证的候选，不以清零Unknown为目标。
- [Risk] 属性轴配置退化为另一套封闭词表 → [Mitigation] 配置与语料发现、开放候选、反例Gate和Schema复用测试同时存在；任何新词不能仅凭词表进入发布层。
- [Risk] 页面改进掩盖底层分类缺陷 → [Mitigation] 先做数据/投影契约和surrogate review，再做视觉优化；Gate失败时不发布完整推荐入口。
- [Risk] Wiki内容缺失或编码异常影响上下文 → [Mitigation] Wiki是可选弱证据；记录NOT_EVALUABLE/失败边界，仍生成不依赖Wiki的字段证据结果。

## Migration Plan

1. 冻结当前字段语义地图和表语义地图输出为只读基线。
2. 生成独立的业务骨架、字段属性轴、语料发现和待复核原因配置，不覆盖旧配置。
3. 用代表性概念生成候选导航与概念详情，输出试做包和审阅包。
4. 完成独立surrogate review，按结果修改配置/规则并重放；未达ACCEPT前不替换现有页面入口。
5. 通过全量确定性、反例和第二Schema/配置检查后，再将新Projection作为可选 review entry。
6. 如新Projection失败，删除或停用其入口即可回滚；原始字段、表语义、Wiki快照和旧页面输出保持不变。
