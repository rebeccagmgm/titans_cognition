## Context

当前仓库已实现全量只读元数据抽取、物理结果对账、静态 Panorama、TRADEFLOW 样本推断和自动评测。现有实现与测试具有保留价值，但项目首页、阶段门、Gold 状态和实际读者交付之间存在冲突：结构工程结果被过度接近地解释为业务认知进展，最新 V1B 运行没有对应的读者业务地图，现有用户确认过程也不足以证明独立业务价值。参见 `proposal.md` 和 `specs/cognition-delivery-governance/spec.md`。

本 Change 是一次契约和状态迁移，不建设新的认知能力。项目已存在 `docs/spec` 详细技术规范，而 OpenSpec 刚刚初始化，因此需要避免长期形成两个互相竞争的产品目标来源。

## Goals / Non-Goals

**Goals:**

- 建立一套最小、明确、可执行的状态分层和完成声明规则。
- 让 README、现有 Spec、案例状态和评估报告对当前实际能力作出一致解释。
- 保留已有工程资产，同时冻结未经业务验收的规模化路线。
- 为后续“有界多源证据底座”和“业务全貌交付”提供稳定前置契约。

**Non-Goals:**

- 不接入 Wiki、系统页面、任务血缘或其他新证据源。
- 不调用 LLM，不设计最终 Prompt 或 Evidence Pack 字段。
- 不生成新的全量业务地图，不修复所有历史运行Artifact。
- 不删除现有 Gate、Gold、Review 或 V1B 实现。
- 不在本 Change 中决定后续业务全貌的完整技术架构。

## Decisions

### 1. 采用五维状态视图，不新增通用状态平台

状态固定拆为：

1. `physical_extraction`
2. `structural_cognition`
3. `reader_delivery`
4. `business_acceptance`
5. `scale_authorization`

每一维使用项目现有文档能够表达的少量状态词，并附范围和证据，不建设新的数据库、服务或通用工作流引擎。

**理由**：问题来自状态含义混淆，而不是缺少状态存储平台。固定五维足以阻止“测试通过即整体完成”的推导。

**备选方案**：沿用 V1A/V1B/V1C 单轴阶段状态。该方案无法区分工程完成、读者交付和业务接受，正是本次偏离的重要原因，因此拒绝。

### 2. OpenSpec治理产品级声明，现有docs/spec保留技术细节

归档后，`cognition-delivery-governance` 作为产品目标、完成声明和授权规则的规范来源；`docs/spec` 继续承载物理契约、推断模型、安全和详细阶段实现。Apply 时必须同步修改 `docs/spec` 中与新治理规范冲突的条目，不允许保留相反口径。

**理由**：一次性迁移全部现有 Spec 风险过高；只建立清晰的规范优先级和冲突清理范围，可以渐进采用 OpenSpec。

**备选方案**：立即将全部 `docs/spec` 搬入 OpenSpec。该方案会把纠偏扩大成文档平台迁移，且容易破坏现有技术契约，因此拒绝。

### 3. 重新解释历史结果，不重写历史Artifact

当前 V1A/V1B 输出、Gold、Review和评估文件保持原样。新的 README 和状态说明将它们标为物理运行证据、结构原型或规则回归证据，并列出不支持的结论。若某个运行含乱码、跨run混用或缺少读者交付，只在当前状态中明确记录，不修改历史文件伪装成同一次成功运行。

**理由**：历史Artifact是偏离诊断和未来回归的重要证据；重写会破坏可追溯性。

**备选方案**：重新生成全部输出并覆盖旧目录。该方案混淆纠偏与新能力建设，也会丢失原始证据，因此拒绝。

### 4. 冻结现有Gate B的放行含义，保留其工程检查用途

现有 Gate B 继续计算候选证据、Unknown、Gold和测量字段，但其状态只能说明旧V1B结构方法是否满足既有工程条件。在新的读者交付和业务验收机制出现前，它不能授权 V1C。Apply 时优先通过文档和状态投影实现该边界；只有代码会自动输出相反授权时，才进行最小代码修改。

**理由**：保留工程回归价值，同时切断循环验证到规模化授权的错误路径。

**备选方案**：删除 Gate B 和全部评估代码。该方案损失已有可复用资产，也超出本次纠偏所需范围，因此拒绝。

### 5. 后续能力使用独立Change

本 Change 完成后，按顺序另行规划：

1. `build-bounded-evidence-foundation`
2. `deliver-and-validate-business-panorama`

这些名称是规划方向，不在本 Change 中预建目录或占位文件。

**理由**：将目标纠偏、证据工程和读者产品分开，能够在每一步重新检查是否仍服务于用户目标。

## Risks / Trade-offs

- [短期内可见能力没有增加] → 将本 Change 控制为小规模契约迁移，完成后立即以新的状态基线规划证据底座。
- [OpenSpec与docs/spec形成双重权威] → 明确产品治理与技术细节的分工，并在Apply任务中逐项消除冲突表述。
- [历史11/11被误认为遭到删除或否定] → 保留全部结果，明确它仍是规则回归证据，只撤回超出证据范围的业务价值解释。
- [状态拆分继续膨胀] → 固定五维，不增加通用状态机、审批平台或新存储。
- [仅改文档但代码仍输出放行状态] → 审计CLI和评估报告中的授权字段；发现冲突时做最小代码修正并增加契约测试。

## Migration Plan

1. 盘点 README、CONTEXT、`docs/spec`、案例配置和CLI报告中的当前目标、阶段和完成声明。
2. 建立一份当前五维状态基线，并为每项列出支持证据与不支持的结论。
3. 同步修改相互冲突的目标、Gate B和V1C授权表述；历史Artifact保持不变。
4. 审计自动报告是否仍会把旧Gate B映射为规模化授权；仅在必要时调整最小代码和测试。
5. 运行文档一致性检查、现有测试和OpenSpec严格校验，确认没有误伤物理抽取能力。
6. 由用户只审核新的目标和当前状态是否准确；不要求用户评审实现机制。

回滚时可恢复本 Change 对受影响文件的差异；历史运行数据和代码底座未被删除，因此不存在数据恢复步骤。
