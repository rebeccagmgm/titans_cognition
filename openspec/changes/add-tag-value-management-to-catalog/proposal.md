## Why

现有标签目录投影只消费了标签维度快照，页面把“标签维度管理”误当成了完整的“标签管理”。真实全量抓取还证明原 `tag-snapshot --scope all` 会在标签列表的 10,000 条查询窗口处提前停止，却错误标记为 `COMPLETE`；因此需要同时修正快照完整性契约，并让阅读页面忠实呈现标签值、标签维度及其关系。

## What Changes

- 以 `tag-values.jsonl`、`tag-dimensions.jsonl` 和标签-维度关联文件建立双对象输入契约。
- 页面使用同一棵“目录 → 标签维度 → 标签”阅读树，通过节点样式和对象标识区分维度与标签，避免用 `tagDimId` 冒充 `tagId`。
- 标签目录节点分别统计标签值和标签维度，并允许从标签跳转到关联维度、从维度查看关联标签。
- 将平台“类型（持仓/组合）”作为标签与标签维度目录树的首层分类；即使源目录未配置，也不得丢失该类型信息。
- 当快照不是 `scope=all`、标签值文件缺失、关联不完整或采集失败时，页面明确显示证据状态，不补造标签记录。
- 保留现有维度 SQL 的格式化、高亮和原始 SQL 证据边界；标签管理侧展示平台返回的标签生成条件等字段。
- 为超过平台单次查询窗口的标签列表使用可校验分片；仅当分片总数守恒、抓取唯一数等于源端期望数且续跑累计计数一致时，快照才可标记为 `COMPLETE`。

## Capabilities

### New Capabilities

- `tag-value-management-catalog`: 从完整标签快照展示标签管理对象、标签维度对象及两者关联，并作为现有标签维度投影的后续扩展。

### Modified Capabilities

无。现有标签维度投影属于前一个独立 Change，新的双对象能力以兼容方式消费其输入，不修改已完成 Change 的契约。

## Impact

- 影响 `titans_cognition.tag_catalog`、CLI 入口及相关测试。
- 修改本机 OpenCLI SZData `tag-snapshot` 的只读分页、续跑和 manifest 完整性判定；不访问业务行、不执行 SQL、不写平台。
- 重新生成一份 `--scope all` 的干净快照作为真实标签管理数据源；现有 dimension-only 快照仍可作为明确的部分输入。
- 修正快照 mapper 对 `tagType/tagClas` 的代码翻译，统一 `1=持仓、2=组合`，并保留原始代码。
